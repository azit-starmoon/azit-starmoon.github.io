# 새 검사 만들기 (AZIT : Star&Moon)

사람이 직접 만들 때도, 예약 작업이 자동으로 만들 때도 이 문서를 따른다.
기준이 되는 구현은 `tests/hsp/`(리커트만 쓰는 가장 단순한 구조), `tests/attachment/`(축 두 개 + 관계별 부), `tests/schema/`(18개 척도 + 순위 문항)다.
막히면 두 검사의 코드를 그대로 본보기로 삼는다.

## 1. 무엇을 만드는가

`assets/js/registry.js`에서 `status: 'soon'`인 검사를 위에서부터 하나씩 연다.

|---|---|---|---|

| `resilience` | 회복탄력성 | 회복탄력성의 세 영역(자기 조절력, 대인 관계력, 긍정성)과 아홉 하위 요인(감정 조절, 충동 통제, 원인 분석 / 소통, 공감, 연결 / 낙관, 감사, 삶의 만족) | 9요인 × 5 = 45문항(5점). 전체와 세 영역, 아홉 요인 지도, 다시 일어나는 힘이 기대는 곳, 키우는 연습(감사 기록 등), 상담 메모. 한국에서 널리 쓰이는 척도(KRQ-53 등)의 문항은 쓰지 않는다 |
| `esteem` | 자아존중감 | (열림) 전반적 자기 가치감(Rosenberg 구성 개념), 나를 대하는 방식(Neff의 자기 자비: 친절 대 비난, 보편성 대 고립, 마음챙김 대 휩쓸림), 자존감이 기대는 곳(Crocker: 인정, 성취, 외모, 관계) | 1부 자기 가치감 10, 2부 나를 대하는 방식 3쌍 × 4 = 24, 3부 기대는 곳 4 × 3 = 12, 모두 5점(약 46문항). 자기 가치감 수준과 흔들림, 친절과 비난의 균형, 기대는 곳 지도, 연습, 상담 메모. 원 척도(RSES, SCS) 문항은 쓰지 않는다 |
| `temperament` | 기질과 성품 | (열림) Cloninger의 기질 4(자극 추구, 위험 회피, 사회적 민감성, 인내력)와 성격 3(자율성, 연대감, 자기 초월). 이름에 TCI를 쓰지 않는다 | 기질 4 × 8, 성품 3 × 8 = 56문항(5점, 차원마다 역문항 2). 기질 유형 8, 성품 모양 4, 기질과 성품의 만남, 연습, 상담 메모 |
| `lifestory` | 생애 이야기 | (열림) McAdams의 삶의 이야기(서사 정체성), 생애 이야기 면담의 핵심 장면, 삶의 의미(Steger: 느끼는 정도와 찾는 정도), 이야기의 결(주도성, 연결, 회복, 의미 엮기) | 1부 의미 10, 2부 글로 답하기 6(`kind: 'text'`, 건너뛰기 가능), 3부 돌아보기 12. 글은 점수에 넣지 않고 공유 링크에서 빠진다 |
| `differentiation` | 자아분화 | (열림) Bowen의 자아분화, Skowron·Friedlander의 네 지표(내 입장 지키기, 감정 반응성, 감정적 단절, 타인과의 융합) | 4 × 8 = 32문항(역문항 2, 가족 장면 9). 분화 지수, 관계 방식 4, 가족 장면, 연습, 상담 메모 |
| `godattach` | 신앙 애착 | (열림) 하나님 애착(attachment to God)의 두 축(Kirkpatrick, Beck과 McDonald). 성인 애착 검사와 같은 유형 이름·기준·지도 | 불안 4갈래 × 3 + 회피 4갈래 × 3 = 24문항(갈래마다 역문항 1). 유형, 여덟 갈래, 사람과의 애착과 함께 보기, 믿음의 연습, 상담 메모 |

- 문항은 **직접 쓴 한국어 문항**이어야 한다. 저작권이 있는 척도(HSPS, VIA-IS, PVQ, DERS, Brief COPE, KRQ-53, RSES, SCS, TCI, MLQ, DSI, AGI 등)의 문항을 옮기거나 번역해 넣지 않는다. 이론의 구성 개념만 빌린다.
- 결과지는 약점 진단처럼 읽히지 않게, 지금의 힘과 키울 방향으로 쓴다. 점수가 낮을 때도 탓하지 않는 말투로 쓴다.
- 요인마다 역문항을 섞는다(대략 4개 중 1개). 같은 요인 문항이 몰리지 않게 섞어 배치한다.
- 문장은 쉬운 일상어, 한 문항에 한 가지 내용. 검사자에게 반말 금지, 존댓말 '~해요' 체.

## 2. 파일 구조 (`tests/<id>/`)

| 파일 | 내용 |
|---|---|
| `items.js` | 척도(`LIKERT_SCALE`: `{value, label}` 배열, value는 1부터), 요인 정의, 문항 `{id, text, ...}`. id는 영문·숫자·`_`만 |
| `scoring.js` | `score(answers)` → 결과 객체. 0~100 점수, 수준(낮음/보통/높음 등), 순위, **응답 점검(`check`)** |
| `content.js` | 해석 글: 요인·유형별 설명, 강점과 주의점, 성장 제안, 상담 질문, 마무리 |
| `chart.js` | 결과지 표지 차트(SVG 문자열을 돌려주는 함수). 첫 화면 카드 그림에도 쓴다 |
| `report.js` | `renderReport(el, rec, ctx)`: 표지 → 목차 → 섹션들. 맨 끝에서 `wireToc(el)` |
| `index.js` | 검사 정의(`export default { id, version: '1.0', title, intro, parts, score, summary, glyph, render }`) |

### 검사 정의 규칙 (`index.js`)
- `parts[]`: `{ id, kind: 'likert'|'pair'|'rank'|'text', title, short, summary, desc, how, count, scale, items }`.
  `text`(글로 답하기)는 문항마다 `{ id, prompt, help, placeholder, rows, max, required }`를 쓰고, 답은 문자열(건너뛰면 빈 문자열)로 남는다.
  건너뛸 수 있는 부는 `skippable: true` (`tests/attachment/index.js` 참고).
- `intro`: `{ kicker: 'AZIT : Star&Moon 검사', lead, facts: [{dt, dd}] (문항, 소요 시간, 구성), gets: [...] }`
- `summary(scores)`: 결과 목록에 보일 한 줄. `glyph(scores)`: 결과 목록 동그라미에 들어갈 1~2글자.

### 결과지 규칙 (`report.js`)
- 섹션은 `<section class="rsec" id="r-<키>">`, 목차는 `<nav class="toc no-print"><div class="toc-inner"><a href="#r-<키>">`.
- 목차 표시는 반드시 `import { wireToc } from '../../assets/js/toc.js'`로 한다. **`scrollIntoView`를 쓰지 않는다**(스크롤이 제자리로 끌려가는 문제가 있었다).
- 필수 섹션: 요약, 자세한 해석, 성장 방향, **상담 메모(`ctx.shared`일 때 숨김)**, 응답 점검.
- 이름 뒤 조사는 받침에 맞춘다(`tests/schema/report.js`의 `jo`/`hasBatchim` 참고).
- 화면 문구에 신뢰를 떨어뜨리는 면책 문구를 넣지 않는다. 응답 점검은 '응답이 고르게 이어졌는지'처럼 담담하게 쓴다.

### 응답 점검 기준 정하기
무작위로 답한 사람과 일관되게 답한 사람을 각각 수천 명씩 흉내 내서 기준값을 정한다.
목표: 일관된 응답은 5% 이하만, 무작위 응답은 60% 이상을 걸러 낸다. 기준값과 그 결과는 `scoring.js` 주석에 남긴다.

### 차트 색
`dataviz` 기준을 따른다. 범주 색은 정해진 순서로 쓰고, 색을 고르면 팔레트 검사 스크립트로 확인한다.
기존 검사에서 검증된 색: `#2a78d6`, `#eb6834`, `#1baf7a`, `#eda100`, `#e87ba4`(이 순서로 인접 대비 통과).

## 3. 연결할 곳
1. `assets/js/registry.js`: 해당 항목을 `status: 'open'`으로 바꾸고 `code`, `items`, `minutes`, `parts`, `gets`를 채운다.
   `code`는 검사 약칭으로 `AZ-` 뒤에 영문 두 글자나 글자와 숫자(예: `AZ-B5`)를 쓰고, 다른 검사와 겹치지 않게 한다. 첫 화면 카드, 검사 소개, 결과지 표지에 함께 보인다.
   같은 파일의 `GROUPS`(첫 화면 분류: 성격과 기질, 마음 건강, 관계와 내면, 강점과 삶의 방향)에서 알맞은 묶음의 `tests`에 id가 있는지 확인하고, 없으면 넣는다.
   고민별 추천 묶음(`BUNDLES`)에 넣을 만하면 순서를 생각해 넣는다. 묶음 하나는 검사 3개, 합쳐 40분 안쪽을 지킨다.
2. `assets/js/pages/home.js`: `GLYPH[<id>]`에 첫 화면 카드 그림(차트 함수에 예시 값) 추가.
3. `assets/js/pages/admin.js`: CSV 내보내기에 이 검사의 핵심 열 추가(`head`와 각 행 모두).
4. `README.md`: 검사 목록과 폴더 구조에 한 줄씩.
5. 결과 목록 동그라미는 `glyph(scores)`가 결과와 함께 저장되므로 따로 손대지 않아도 된다.
6. `assets/js/itemstats.js`: `SCALE_DEFS[<id>]`에 척도로 묶는 기준(문항의 어느 필드로 묶는지, 척도 이름, 순서)을 넣는다. 리커트 문항만 쓰고, 역채점은 문항의 `r: true`나 `key: -1`로 알아본다. 넣지 않으면 관리 화면 문항 분석에서 그 검사를 계산할 수 없다.
7. 다른 검사와 같은 마음을 다른 각도로 재는 검사라면(예: 성인 애착과 신앙 애착), `assets/js/pairs.js`의 `PAIRS`에 짝을 하나 더한다. 두 검사를 모두 한 검사자의 종합 결과지에서 나란히 읽어 준다. 연구로 관련이 보고된 짝만 넣고, 점수는 `agree()`(높음 60 이상, 보통 40~59, 낮음 40 미만)로 비교한다.

## 4. 점검
```bash
python3 tools/smoke.py --only <id> --shots /tmp/shots   # 새 검사만 빠르게
python3 tools/smoke.py                                    # 올리기 전에 전체
```
- 둘 다 `{"ok": true}`여야 올린다.
- 채점 검증: `node tools/validate.mjs --only <id>`. 모의 응답자로 ① 문항마다 제 척도를 맞는 방향으로 움직이는지(역채점 누락, 점수에 안 들어가는 문항), ② 숨은 성향 복원, ③ 재검사 점수 상관과 유형 일치율, ④ '그렇다' 쏠림에 대한 흔들림, ⑤ 무작위·중립 응답에서 유형 쏠림, ⑥ 응답 점검이 짚는 비율을 본다. ①은 '이상 없음'(점수에 안 들어감 0, 방향 어긋남 0)이어야 올린다. 새 검사는 `tools/validate.mjs`의 `CATS`(결과 이름 자리)와, 유형을 기준선으로 가르면 `NEAR`에도 한 줄 넣는다.
- 캡처(390px 휴대폰)로 소개, 문항, 결과지 표지와 섹션 몇 곳을 눈으로 확인한다. 글자 넘침, 겹침, 어색한 조사를 고친다.

## 6. 하지 말 것
- 잠금 번호(검사 코드, 결과 잠금 번호)를 원문으로 저장소에 쓰지 않는다. `config.js`에는 해시만 있다.
- `firebase/database.rules.json`은 바꾸지 않는다(바꿔도 사용자가 콘솔에 붙여 넣어야 적용된다).
- 이미 열린 검사의 채점, 문항, `version`을 바꾸지 않는다. 저장된 결과와 진행 중인 검사가 깨진다.
- 실제 사용자 데이터에는 손대지 않는다. 점검은 체험 모드(`?demo=1`)로만 한다.

## 7. 예약 작업(자동) 규칙
한 시간마다 도는 예약 작업은 아래 순서를 따른다.
1. **진단**: `origin/main`으로 `python3 tools/smoke.py`, `gh run list -R azit-starmoon/azit-starmoon.github.io -L 3`으로 배포 상태 확인.
   smoke가 실패하면 원인이 분명하고 작게 고칠 수 있을 때만 고쳐서 다시 smoke를 통과시킨 뒤 올린다.
2. **작업 자리 잡기** (검사마다 따로 잡는다. 서로 다른 검사는 동시에 만들어도 된다)
   - 원격 `auto/<id>` 브랜치 가운데 `<id>`가 이미 `origin/main`의 registry에서 `open`인 것은 끝난 작업이라 무시한다(브랜치 삭제가 막혀 있어 남아 있을 수 있다).
   - registry의 `soon` 검사를 위에서부터 보면서 고른다.
     - 그 검사의 `auto/<id>` 브랜치가 없으면 맡는다. 빈 커밋을 만들고 `git push --force-with-lease=refs/heads/auto/<id>: origin HEAD:refs/heads/auto/<id>`로 자리를 잡는다. 실패하면 다른 회차가 방금 잡은 것이니 다음 검사로 넘어간다.
     - 브랜치가 있고 마지막 커밋이 90분 안이면 다른 회차가 작업 중이다. 다음 검사로 넘어간다.
     - 90분이 넘었으면 멈춘 작업이다. 그 브랜치를 이어받는다(먼저 빈 커밋을 올려 자리를 표시).
   - 맡을 검사가 없으면 진단만 하고 끝낸다.
3. **만들기**: 이 문서대로 만든다. 30분을 넘기지 않게 브랜치에 커밋을 올려 진행을 남긴다(작업 중이라는 표시도 된다).
4. **마무리**: 전체 smoke 통과 → `origin/main` 위에 squash로 합쳐 version 갱신 후 main에 올린다 → `auto/<id>` 브랜치 삭제를 시도한다(세션에서는 삭제가 막혀 있을 수 있다. 실패해도 괜찮다. 위 규칙대로 무시된다).
   main에 올리는 push가 거절되면 다른 회차가 먼저 올린 것이다. 다시 fetch해서 최신 `origin/main` 위에 squash로 합치고(충돌은 양쪽을 모두 살리는 쪽으로 해결), version을 다시 찍고, 전체 smoke를 통과시킨 뒤 올린다.
5. 열 검사가 더 없고 남은 작업 브랜치도 없으면 진단만 한다.
